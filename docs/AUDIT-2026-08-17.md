# Repository and packaging audit — 2026-08-17

An audit of open-source readiness and cross-platform behavioral consistency, judged from the
perspective of a .NET MAUI developer who finds the package on NuGet, installs it, and tries to
send a file between two phones — without being able to ask the maintainer a question.

**Scope:** branch `merge/refactor-into-preview`, commit `61786fd`.
**Evidence base:** three TFM builds (`net10.0`, `net10.0-android`, `net10.0-ios`), the unit test
suite via `dotnet run`, a Release `dotnet pack` with nupkg/snupkg inspection, doc samples compiled
against the built assembly, and file reads at every cited line. Items not verified this way are
labeled unverified.

---

## Verdict

**Not ready for 1.0. Ready-adjacent for a preview.** Two things stood in the way, and neither is
packaging:

1. ~~**The library breaks its own cross-platform promise in the core flow.**~~ **Fixed
   2026-08-17.** Reconnect after a disconnect worked on Android and failed on iOS, and `SendAsync`
   failure threw a typed `NearbyException` on one platform and a raw SDK exception on the other —
   in both directions. These were exactly the "fix applied to one partial, not its sibling" defects
   the repo warns itself about (findings 1, 2, 6). See each finding for what changed.
2. ~~**The README teaches an API that does not exist.**~~ **Fixed 2026-08-17.** The data-binding
   walkthrough claimed change notification the types do not implement, and the Configuration table
   contained a removed option, omitted three real ones, and named four others wrongly, so the
   stranger's first hour failed silently or with CS1061 (findings 3, 4, 5, plus 9 and 17). Every
   Configuration row now compiles against the real assembly.

**Both original blockers are now closed**, along with the documentation tier behind them —
findings 7, 8, and 18 were fixed on 2026-08-17, so the public XML docs and `PAYLOAD-DELIVERY.md` now
describe the design the code actually implements.

What remains before 1.0 is one documentation item and three process items: the `AddNearby`/
`UseNearby` param doc that promises working platform defaults where iOS throws without a
`ServiceId` (finding 10), fork-hostile CI (finding 11), the disagreeing version records
(finding 15), and the missing `SECURITY.md` plus issue templates (finding 16).

The areas you might expect to be the problem are not. Packaging is clean end to end: the packed
`.nupkg` carries the embedded README, icon, MIT expression, per-TFM libs with XML docs, and repo
URL pinned to a commit. The `.snupkg` has working SourceLink. The publish pipeline (MinVer tag →
vulnerability gate → OIDC push → generated release notes) is real and good. All three TFMs build
warning-free and 250/250 unit tests pass. The public API surface is unusually consistent —
identical baselines across TFMs, no vendor vocabulary, tokens everywhere, typed exceptions only.

## Findings, ranked

### ~~1. Every iOS teardown path drops the native peer handle while the device row stays `Visible`, so reconnecting works on Android and throws on iOS~~

> **Fixed 2026-08-17.** The reject, connection-dispose, and remote-disconnect-control-message paths
> in `Native/PlatformNearby.ios.cs` no longer call `Peers.Remove`, so a disconnected peer keeps its
> `MCPeerID` handle and stays reconnectable. Only the `NotConnected` branch — the one path that also
> reports the loss via `WriteDeviceLost` — still removes. `DisposeSessionIfLastPeer` became
> `DisposeSessionIfIdle` and now keys off `_activeConnections.IsEmpty` instead of `Peers.IsEmpty`,
> because peers now outlive their connections. Two device tests that encoded the old behavior were
> updated and one was added for the local-disconnect path.

- **Evidence:** `Native/PlatformNearby.ios.cs:524` (dispose lambda: `Peers.Remove(id)`), `:142`
  (reject lambda), `:593` (remote-disconnect control message). `PlatformInitiateConnectAsync`
  (`ios.cs:236-241`) faults with `NearbyException` "not currently visible" when the handle is
  gone. Android connects by string id (`android.cs:386-395`) and is unaffected.
  `docs/DEVICE-LIFECYCLE.md` documents `Connected → Visible → Connecting` as valid with no iOS
  caveat.
- **Experience:** the user disconnects, the row shows `Visible`, they tap connect again. Android
  connects. iOS throws until `DiscoveryRefreshInterval` (default 30 s) re-finds the peer — and
  with that option set to `null`, the row is poisoned permanently.
- **Fix:** on iOS, keep the `MCPeerID` handle on every path where the row stays `Visible`. Remove
  it only where `WriteDeviceLost` also fires. Audit `DisposeSessionIfLastPeer` (reads
  `Peers.IsEmpty`) in the same change.

### ~~2. `SendAsync` failure surfaces a different exception type per platform, in both directions~~

> **Fixed 2026-08-17.** Both Android send paths now wrap a raw GMS fault in
> `NearbyTransferException` and log it (`LogSendBytesFailed` / `LogSendFileFailed`, existing
> EventIds), and the iOS file-send catch wraps instead of rethrowing. Cancellation and the
> inactivity-timeout paths are unchanged — the new catches filter out `OperationCanceledException`
> and `NearbyException` so they run last. The secondary defect noted under finding 3 of the platform
> pass is fixed with it: iOS now observes `transfer.Completion`, which it never awaits, so a
> terminal `Report(Failure)` no longer leaves an unobserved faulted task.

- **Evidence:** Android byte and file sends await `client.SendPayloadAsync` with no catch
  (`android.cs:504`, `:537`; the file path's catch chain at `:544-562` covers only cancellation) —
  a GMS `ApiException` escapes raw and unlogged. iOS wraps the same failure in
  `NearbyTransferException` (`ios.cs:318`). Mirror image on file completion: iOS's generic catch
  rethrows raw (`ios.cs:414-419`) where Android faults typed via `OutgoingTransfer`
  (`Transfer/OutgoingTransfer.cs:60-63`). `NearbyConnection`'s XML docs promise
  `NearbyTransferException`. The repo already fixed this exact crash class on the connect path
  (`android.cs:399-407` comment).
- **Experience:** `catch (NearbyException)` around a send works on one platform and lets the app
  crash on the other. This is the file-transfer scenario, the plugin's headline use case.
- **Fix:** wrap the two Android `SendPayloadAsync` awaits in the catch-log-wrap shape iOS uses,
  and change iOS's `throw;` at `ios.cs:419` to `throw new NearbyTransferException(..., ex)`.

### ~~3. The README's binding story is false: `NearbyDevice` raises no `PropertyChanged` and `Devices` implements no `INotifyCollectionChanged`~~

> **Fixed 2026-08-17.** Both sentences in the **Device state** section were rewritten. The README now
> says a `NearbyDevice` is an immutable snapshot and a status change arrives as an `Updated` entry on
> `Devices.Changes` (verified against `NearbyDeviceChangeAction.Updated` in the public API baseline),
> and that `nearby.Devices` is a read-only snapshot list which raises no change notification — so
> binding it directly renders once and never updates. It points at `NearbyDeviceCollection` for
> binding, which is the type that actually implements `INotifyCollectionChanged`.

- **Evidence:** `README.md:193` ("the device raises `PropertyChanged`, so a bound row updates in
  place") vs `Devices/NearbyDevice.cs:27` — `public sealed record`, `init`-only, no
  `INotifyPropertyChanged` anywhere in `Devices/`. `README.md:204` ("`Devices` implements
  `INotifyCollectionChanged`, so you can bind it straight to a `CollectionView`") vs
  `Devices/INearbyDevices.cs:21` — `IReadOnlyList<NearbyDevice>` only. Change notification exists
  only on `NearbyDeviceCollection<TRow>` (`NearbyDeviceCollection.cs:49`).
- **Experience:** the developer binds `nearby.Devices` per the walkthrough. The list renders once
  and never updates. No exception, no log — a silent dead UI in step 3 of getting started.
- **Fix:** rewrite both sentences to the real mechanism: status changes arrive as entries on
  `Devices.Changes`, and binding goes through `NearbyDeviceCollection` (which the README already
  shows at lines 285-302).

### ~~6. `ConnectTimeout = Timeout.InfiniteTimeSpan` does not wait indefinitely on iOS~~

> **Fixed 2026-08-17.** `PlatformInitiateConnectAsync` now converts the timeout through a new
> `ToInvitationTimeout` helper, which maps `Timeout.InfiniteTimeSpan` to 24 hours rather than
> passing -1 s to `InvitePeer`. The deadline stays owned by `AwaitHandshakeAsync`, which already
> skips its own deadline for infinite. **Still unverified on hardware:** MPC's substitution of a
> 30-second default for a non-positive timeout is from Apple's documentation, so the original defect
> and this fix both rest on that, not on a device run.

- **Evidence:** `ios.cs:257` passes `_options.ConnectTimeout.TotalSeconds` (negative for infinite)
  straight to `InvitePeer`. Apple documents that a non-positive timeout gets MPC's own 30-second
  default. `Options/NearbyOptions.cs:135-137` promises indefinite waiting. Android honors it (the
  only deadline is `AwaitHandshakeAsync`'s, skipped for infinite). MPC's substitution is from
  Apple documentation, not device-tested.
- **Experience:** with the documented opt-out set, Android waits forever, iOS fails after ~30 s
  with a `NearbyException` that never mentions a timeout.
- **Fix:** map `InfiniteTimeSpan` to a large positive value at `ios.cs:257`, or document the iOS
  floor on the member.

### ~~7. The public XML docs claim delivery on the platform SDK's callback thread; the pump delivers on thread-pool threads~~

> **Fixed 2026-08-17.** All three passages now state thread-pool delivery and explicitly deny the
> SDK callback thread: `INearby.cs` (the `Thread safety` remark, which also tells consumers not to
> rely on the SDK's thread or its ordering), `Devices/INearbyDevices.cs`, and
> `Connections/NearbyConnection.cs` (`ReceiveAsync`). Two further changes came out of the sweep:
> `NearbyConnection.InboundProgress` was **left claiming the platform callback thread, because that
> claim is true** — `Report` is invoked directly from inside both SDK callbacks
> (`PlatformNearby.android.cs:280`, `PlatformNearby.ios.cs:636`) with no channel between — and its
> doc now names that asymmetry against `ReceiveAsync`/`Changes` so it does not read as an oversight.
> `Native/IPlatformNearby.cs` said "Consumers must marshal to the UI thread", ambiguous between the
> internal caller and an app; it now states that the SDK thread never reaches an application.

- **Evidence:** `INearby.cs:23-24` ("Platform callbacks arrive on background threads owned by the
  platform SDK, and that is the thread `INearbyDevices.Changes` delivers on"),
  `Devices/INearbyDevices.cs:11-12`, `Connections/NearbyConnection.cs:274`. AGENTS.md states the
  opposite invariant ("Do not document or rely on the SDK's callback thread reaching consumers: it
  does not"), and `README.md:279-282` agrees with AGENTS.md.
- **Experience:** IntelliSense teaches a wrong threading model — for example the iOS serial-queue
  ordering the claim implies. The practical advice (marshal yourself) survives, but the mechanism
  is false.
- **Fix:** reword the three passages to "a thread-pool thread — never the UI thread".

### ~~12. When a connected iOS peer drops, the row's fate depends on a pump race; Android is deterministic~~

> **Fixed 2026-08-17.** Fixed in shared code rather than in the iOS partial, because the race is in
> the consumer of the lost event, not its producer: `NearbyImplementation.OnDeviceEvent` now skips
> removal for any device that still has an entry in `_activeConnections` or `_pendingRequests`,
> which makes the outcome independent of whether the lost event or `WatchDisconnectAsync`'s
> `ResetToVisible` lands first. Eviction of a genuinely departed device remains the refresh loop's
> `BeginGeneration`/`EvictUnconfirmed` pair. The stale comment in the iOS `NotConnected` branch,
> which claimed the session ignores the lost event for a `Connected` device, was corrected — by
> then `ReleaseConnection` has already run, so the guard is what protects the row.
>
> **Not covered by a new regression test, deliberately.** Two attempts were written and both were
> discarded after being checked against the pre-fix code: each passed without the guard, because the
> `Connected` status check already blocked eviction in the ordering they exercised. The window the
> guard actually closes is between `DisconnectAsync` disposing the connection and
> `WatchDisconnectAsync` clearing `_activeConnections`, which the public API cannot open
> deterministically. A test that cannot fail without the fix is worse than no test, so none was
> added.

- **Evidence:** `ios.cs:531-547` runs `ReleaseConnection` (→ `ResetToVisible` on a separate
  continuation, `NearbyImplementation.state.cs:261-273`) before `WriteDeviceLost`, whose handler
  removes any row already `Visible` (`state.cs:109-113`). Android writes no lost event on
  disconnect (`android.cs:150-164`). The surrounding paths were verified directly; the exact
  ordering claim rests on code reading, not a line-by-line trace.
- **Experience:** a dropped iOS peer's row nondeterministically disappears or returns to `Visible`
  (and per finding 1, an unconnectable `Visible`). `docs/DEVICE-LIFECYCLE.md:37` documents one
  outcome.
- **Fix:** make the outcome order-independent — write the lost event before `ReleaseConnection`,
  or have the lost handler skip devices with an active connection entry.

## What does not matter

- **NuGet packaging and symbols** — nothing to do. Metadata, icon, embedded readme, license
  expression, SourceLink, snupkg, deterministic CI build, and OIDC trusted publishing are all
  present and verified in the packed output.
- **Code of conduct, FUNDING, more templates** — optional for a single-maintainer repo.
  `SECURITY.md` is the only one worth doing before 1.0.
- **Doc-sample rot at scale** — it does not exist. 22 of 23 samples compile verbatim against the
  real DLL. The docs' problem is the handful of stale *claims*, not the code blocks.

## Verified clean

- Builds: all three TFMs, warning-free (exit 0 each). Unit tests: 250/250 via `dotnet run`.
- Public API: all three baselines byte-identical, `Native/` quarantine holds, no vendor vocabulary
  in identifiers, every async I/O method takes a `CancellationToken`, failures are typed
